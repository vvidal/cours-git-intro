Git dans Apache NetBeans (2h)

Suite du cours après les 4h de bases Git

  • Flèches clavier : slide précédente/suivante.
  • Touche F : activer/désactiver le plein écran.
  • Touche Home : revenir à la première slide.

Objectifs du module

  • Relier les actions Git de la ligne de commande aux actions NetBeans.
  • Réaliser un cycle complet : modifier, commit, push, pull.
  • Gérer une branche et résoudre un conflit simple.

Pré-requis

  • Avoir suivi le module "Bases de Git (4h)".
  • Avoir un dépôt local déjà configuré (nom/email/remote).
  • Connaître status, add, commit, push, pull, branch, merge.

Étape 1 : créer le projet Java

  • Dans NetBeans : Fichier > Nouveau projet.
  • Choisir Java Application avec Ant ou Maven selon le besoin.
  • Créer une structure claire dès le départ (nom de projet explicite).

Étape 2 : initialiser Git dans NetBeans

  1. Clic droit sur le projet.
  2. Versioning > Initialize Git Repository.
  3. Vérifier la création du dépôt local (.git).

Étape 3 : configurer identité Git

Option terminal (globale, une seule fois)

git config --global user.name "NOM PRENOM"
git config --global user.email "prenom.nom@etu.univ-lyon1.fr"

Option NetBeans (locale, prioritaire)

  1. Clic droit sur le projet > Git > Repository > Open Configuration.
  2. Copier ce bloc à la fin du fichier de configuration ouvert, puis enregistrer :
[user]
    name = NOM PRENOM
    email = prenom.nom@etu.univ-lyon1.fr

Étape 4 : premier commit

  1. Créer/adapter .gitignore avant le premier commit. Pensez à ajouter ce fichier au dépôt (racine du dépôt)...
  2. Clic droit sur le projet > Git > Commit…
  3. Sélectionner les fichiers, écrire un message clair, valider.

Voir l'historique : Git > Show History.

Exemple .gitignore (Java/NetBeans)

Étape 5 : lier un dépôt distant

Option terminal

git remote add origin https://forge.univ-lyon1.fr/<identifiant>/<depot>.git
git push -u origin master

Utiliser main au lieu de master si nécessaire.

Option NetBeans (nécessite de créer un dépôt distant vide en amont, même pas de README.md)

  1. Clic droit sur le projet > Git > Remote > Push…
  2. Renseigner nom remote, URL et identifiants (PAT recommandé : Personal Access Token, jeton personnel d'accès).
  3. Choisir branche de suivi (master ou main, rester cohérent).

Push suivants : Git > Remote > Push to Upstream.

Étape 6 : travail quotidien

Après modifications locales

  1. Git > Commit…
  2. Si la branche distante a avancé : Git > Remote > Pull from Upstream, résoudre les conflits si besoin, puis Git > Remote > Push to Upstream.
  3. Si la branche distante n'a pas avancé : Git > Remote > Push to Upstream (ou Push…).

Pour récupérer des changements

  1. Git > Remote > Pull from Upstream (ou Pull…).

Conseils et vérifications

  • Commiter souvent (un commit = modifications cohérentes).
  • Toujours renseigner un message de commit explicite.
  • Vérifier l'identité Git active :
git config user.name
git config user.email

Un dépôt local peut pointer vers plusieurs remotes (GitHub, GitLab, Forge, fork).

Cloner un projet existant

  • Dans NetBeans : Team > Git > Clone…
  • Renseigner l'URL du dépôt distant.
  • Choisir le dossier local et la branche à ouvrir.
  • Construire puis lancer le projet pour valider l'environnement.

Exercice collaboratif (30 à 45 min)

Projet : mini application Java de gestion de bibliothèque.

  • Objectif : produire une version compilable en fin de séance.
  • Fonctions minimales : ajouter, supprimer, afficher des livres.
  • Contrainte : chaque membre travaille sur une branche dédiée.

Répartition des tâches

  • Chef de projet / Intégrateur : entérine le système de build officiel (Ant, Maven, Gradle, etc.) et la structure du projet versionnée dans Git, valide les interfaces, arbitre les choix techniques, coordonne les merges.
  • Équipe 1 (métier: Developer) : classe Book (title, author, ISBN).
  • Équipe 2 (métier: Developer) : classe Library (collection + méthodes).
  • Équipe 3 (vue: Developer) : interface CLI (menu, saisie, actions).
  • Équipe 4 (Qualité: tests et fusions: Maintainer) : tests unitaires (JUnit) sur Book/Library.
  • Pour tous (premier qui commit) : README.md + JavaDoc + .gitignore (le même pour tous).

Pour créer des groupes : https://forge.univ-lyon1.fr/dashboard/groups.

Contrat d'interfaces (obligatoire)

But : chaque équipe développe une partie compatible avec les autres.

Classe Book (public minimum)

public class Book {
    public Book(String title, String author, String isbn)
    public String getTitle()
    public String getAuthor()
    public String getIsbn()
    public void setTitle(String title)
    public void setAuthor(String author)
    public void setIsbn(String isbn)
    public String toString()
}

Classe Library (public minimum)

public class Library {
    public void addBook(Book book)
    public boolean removeBookByIsbn(String isbn)
    public Book findBookByIsbn(String isbn)
    public java.util.List<Book> listBooks()
    public int countBooks()
}

Règle : aucune équipe ne modifie ces signatures sans validation du chef de projet.

Workflow Git attendu

  1. Cloner le dépôt partagé.
git clone https://forge.univ-lyon1.fr/<identifiant>/<depot>.git
  1. Créer une branche personnelle.
git checkout -b prenom-tache
  1. Commiter régulièrement, puis pousser la branche.
git add .
git commit -m "message clair"
git push origin prenom-tache
  1. Le chef de projet relit les Merge Requests et ne fusionne que les branches compatibles avec l'architecture décidée.

Fusion et critères de réussite

  • Fusion via Merge Request / Pull Request vers la branche principale.
  • En cas de conflit : Pull, résolution locale, nouveau commit, Push.
  • Le projet doit compiler et lancer un scénario de démonstration.
  • L'historique montre des commits lisibles et une contribution de chaque membre.

Fin du module

  • Cycle attendu en autonomie : Commit puis synchronisation avec la branche distante (Pull si nécessaire, puis Push).
  • Penser à garder des commits petits, lisibles et réguliers.
  • Retour au portail pour revoir les bases ou télécharger le plan.
